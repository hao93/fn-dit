# 版本发布流程

## 当前发行方式

v0.1.6 是 GitHub 的公开手动安装发行版，未签名。开发者和发布者为 fancy。不是飞牛官方商店上架包，也没有厂商签名。用户已明确选择先提供未签名手动安装版。

## 维护者操作

1. 准备代码、变更说明和文档，将 `package.json`、`fnos/manifest`、UI 版本同步到新的版本。
2. 更新 `docs/releases/v<版本>.md`，写清功能、安装要求、升级流程、签名状态和未验证范围。
3. 更新普通测试工作流和发布工作流中的版本化文件名。
4. 在 `.release/request.json` 明确填写版本、`unsigned: true` 与 `channel: manual-install`，提交到 main。这个文件的变化会触发 **Publish Release**，普通提交不会自动发布。
5. 等待构建与验证完成，检查 Release 页面、资产 SHA-256、标签对应提交和 Latest 状态。

发布脚本只接受仓库 `hao93/fn-dit`、具体源提交以及与项目一致的请求版本，不会移动既有版本标签，也不会覆盖已经公开的 Release。需要修正公开包时使用新的版本。

## 自动流程

- 固定来源与哈希下载官方 Linux fnpack 1.3.3。
- 运行 Node.js 回归，再构建 `fn-dit-<版本>-unsigned.fpk`。
- 对实际发行 FPK 运行包回归、审计与服务启停/历史/扫描计划测试。
- 核对发布请求、版本、FPK 审计和校验文件；生成构建信息、中文安装指南和所有附件校验清单。
- 创建指向本次源提交的版本标签与 Release 草稿。
- 上传全部附件，核对服务器返回的文件大小与 SHA-256。
- 附件完整后公开 Release，设为非预发布版及 Latest，再读取确认。

GitHub 的非预发布标记表示仓库的发行渠道，不表示已经获得飞牛签名或完整实机验证。说明中须始终保留两者的区别。

## Release 附件

| 附件 | 作用 |
| --- | --- |
| `fn-dit-<版本>-unsigned.fpk` | 手动安装包 |
| `.fpk.sha256` | 安装包校验值 |
| `.fpk.audit.json` | 包结构、入口、权限、源码一致性等审计 |
| `INSTALL.zh-CN.md` | 中文快速安装教程 |
| `BUILD-INFO.json` | 源提交、工具版本/哈希、签名状态、验证流程 |
| `SHA256SUMS.txt` | 所有上述附件的校验清单 |

GitHub 自动提供的 Source code ZIP/tar.gz 是源码归档，不是安装包。

## 权限与失败处理

发布使用当前仓库 Actions 的短期 `GITHUB_TOKEN`，仅发布任务需要 contents 写权限，不存储个人 token。脚本不打印令牌。验证或上传失败时不公开新 Release；同源提交的草稿可重新生成附件，已有公开 Release 不会被覆盖。

CI 同时保留构建证据。若自动发布失败，应先检查工作流日志、仓库 Actions 权限与 API 错误，修正后再运行。不要把不完整附件的草稿当成已交付版本。
